얼굴은 그대로,
헤어스타일만 바꿔서 미리 봅니다.

목표 제품: 고객 얼굴을 촬영하고 원하는 참고 헤어를 고르면, 정체성은 유지한 채 스타일만 적용한 예상 이미지와 5초 영상을 만들어 상담에 씁니다. 이 문서는 그 설계된 서비스를 어떻게 쓸지(사용자)와 지금 코드를 어떻게 돌리고 확장할지(개발자)를 한 곳에 담되, 지금 실제로 되는 범위를 칩으로 정직하게 구분합니다.

시술 전
→
AI 예상 결과
유지: 얼굴·이목구비·피부톤·표정·배경  ·  변경: 길이·앞머리·컬·가르마·색·볼륨

사용자 문서 · 01

서비스 소개

이 절은 “목표 제품”의 설계를 설명합니다. 아래 흐름·정책은 제품이 지향하는 모습이며, 지금 v0.1에서 실제로 동작하는 범위는 각 항목의 상태 칩과 지금 되는 것/예정·3구간 라벨을 보세요.

HairView AI는 미용실 상담을 돕는 도구로 설계됐습니다. 단순한 “AI 영상 사이트”가 아니라 빠른 미리보기 → 고품질 스타일 합성 → 자연스러운 영상 시뮬레이션을 잇는 상담 시스템을 지향합니다. 설계상 핵심은 영상보다 먼저 얼굴 정체성을 지킨 결과 이미지를 확정하고, 그 한 장을 영상으로 바꾸는 순서입니다 (현재 이미지·영상의 실제 생성은 로드맵, 흐름 골격은 Mock).

설계 원칙상 참고 사진은 “그대로 복사”하지 않습니다. AI가 참고 헤어를 구조(길이·앞머리·컬·색 등)로 분해해 고객 얼굴에만 그 요소를 적용합니다 — “특정 연예인으로 바꿔 달라”가 아니라 헤어 특징만 빌려오는 방식입니다. (지금은 분석이 Mock으로 고정 예시를 반환합니다.)

누가 쓰나요

미용실(주 사용자)

헤어 디자이너·퍼스널컬러·웨딩·뷰티 콘텐츠 제작자. 상담과 콘텐츠 제작에 활용합니다.

사용자 문서 · 03

상담은 이렇게 흘러갑니다

아래는 상담이 진행되도록 설계된 순서입니다(대부분 단계는 아직 로드맵). 각 단계 오른쪽 칩이 지금 버전의 실제 상태입니다.

구현·검증완료 Mock(모의) 로드맵(예정)

  1. 사진 촬영 또는 업로드 로드맵

    브라우저 카메라로 정면 사진을 찍거나 기존 사진을 올립니다. 앱 설치가 필요 없습니다.

  2. 촬영 품질 검사 로드맵

    얼굴이 한 명인지, 너무 작지 않은지, 정면에 가까운지 등을 기기에서 먼저 확인합니다(MediaPipe).

  3. 참고 헤어 입력 로드맵

    참고 사진 업로드·카탈로그 선택·텍스트 설명 중 하나로 원하는 스타일을 전달합니다.

  4. 스타일 구조 분석 Mock

    AI가 참고 헤어를 길이·앞머리·컬·색 등 구조로 분해합니다. 지금은 모의 분석 결과가 반환됩니다.

  5. 스타일 추천 로드맵

    얼굴형에 맞춘 추천 3가지와 이유·난이도·추천 컬러를 제안합니다. (미모·매력 점수는 매기지 않습니다.)

  6. 합성 이미지 3장 생성 로드맵

    참고 최유사 / 얼굴형 보정 / 관리 쉬운 현실형 3가지를 만들어 비교합니다.

  7. 영상 생성 Mock

    고른 이미지 한 장을 5초·9:16 영상으로 바꿉니다. 지금은 모의 Provider로 전체 흐름(요청→상태→완료)만 동작합니다.

  8. QR·링크 공유 로드맵

    결과를 QR이나 공유 링크로 고객에게 전달합니다.

  9. 상담 기록 저장 로드맵

    상담 내용을 매장 고객 기록에 남깁니다(설계 원칙: 사진 없이 텍스트 중심).

사용자 문서 · 04

개인정보와 동의

아래는 지켜야 할 정책·설계 원칙입니다(구현은 로드맵). 얼굴을 다루는 화면(카메라·업로드·생성)이 붙을 때 이 원칙대로 구현합니다. 값(저장 기간 등)은 기획 기준 예시로 확정 전입니다.

얼굴 사진은 개인정보로 다룹니다. 서비스는 고객을 인증·식별하려고 얼굴 특징을 쓰지 않고, 얼굴 임베딩을 장기 저장하지 않는 것을 원칙으로 합니다.

  • 생성 전, 외부 AI로 사진이 전송될 수 있다는 점과 저장 기간·삭제 방법을 안내한다(원칙).
  • 동의는 4가지로 나뉜다: 얼굴 처리 · 외부 AI 전송 · 저장 · 결과 공유. 동의 없이 생성 API를 호출하지 않는다.
  • 저장 기간(기획 기준 예시, 확정 전): 참고 사진은 분석 직후 삭제 · 고객 원본은 기본 24시간 또는 상담 종료 후 · 결과는 7~30일.
  • 브라우저에 얼굴 사진을 저장하지 않는다(localStorage·IndexedDB 등 금지) — FE 컨벤션.
  • 연예인 참고 사진은 헤어 요소만 뽑고 원본은 삭제하며, 이름은 저장·광고에 쓰지 않는다.

영상 생성 요청 · 응답

// POST /api/v1/video-generations  →  202
{ "consultation_id": "...", "image_asset_id": "...", "prompt": "turn head...",
  "duration_seconds": 5, "aspect_ratio": "9:16", "quality": "720p",
  "idempotency_key": "..." }        // image_asset_id = asset id (URL 아님), duration ∈ {5,8}

// 202 응답
{ "generation_id": "uuid", "status": "SUBMITTED" }

// GET /api/v1/generations/{id}  →  200 (image·video 공통)
{ "generation_id":"uuid", "generation_type":"VIDEO", "status":"PROCESSING",
  "provider":"MOCK", "estimated_cost_usd":0.0, "error_code":null }

오류는 항상 이 형태(envelope)

{ "error": { "error_code": "NOT_FOUND", "message": "...", "request_id": null } }

성공 응답은 envelope로 감싸지 않으므로 클라이언트는 HTTP status로 분기합니다. 404 → NOT_FOUND, 422 → VALIDATION_ERROR, 미처리 예외 500 → INTERNAL_ERROR(스택 미노출).

개발자 문서 · 04

생성 상태 · 흐름

생성은 즉시 끝나지 않습니다. 202 + generation_id로 접수하고, Worker가 Provider를 폴링/Webhook으로 따라가며 상태를 전이시킵니다. FE는 GET .../generations/{id}로 폴링합니다.

CREATED → UPLOADING → SUBMITTED → QUEUED → PROCESSING → POST_PROCESSING → SUCCEEDED → EXPIRED
                                              └────────────────────────────▶ FAILED / CANCELED
  • 상태 전이 규칙은 domain/state_machine.py 한 곳에서만 관리(타입별: IMAGE는 POST_PROCESSING 없음).
  • Provider가 중간 상태를 건너뛰고 완료를 알려도 정체되지 않도록 전방 스킵을 허용.
  • 역행·중복·순서 뒤바뀜 이벤트는 no-op(무시) — 이미 SUCCEEDED인 작업을 늦은 이벤트로 되돌리지 않음.
  • 영상은 provider SUCCEEDED → 내부 POST_PROCESSING(후처리 대기), Worker 완료 시 SUCCEEDED.

개발자 문서 · 06

Provider 추상화 · Mock

외부 AI는 공통 인터페이스(base.py) 뒤에 둡니다. Service는 특정 Provider 전용 필드에 의존하지 않습니다. 기본값은 Mock(외부 키·비용 불필요).

image_analysis
사진·헤어 구조 분석 (Gemini 예정)
image_generation
얼굴 유지 헤어 합성 (Gemini 편집 예정)
studio_draft
Studio script/storyboard 초안 생성 (MOCK 기본, backend-only local OLLAMA 옵션)
video_generation
이미지→영상 (Provider는 env/Registry로 교체 — PixVerse·fal·Wan 계열 후보, 모델명·가격은 unverified·하드코딩 안 함)

Mock 영상 Provider는 8가지 시나리오를 결정적으로 재현합니다: SUCCESS · SLOW · SUBMIT_FAIL · RATE_LIMIT · NO_BALANCE · POLICY_BLOCK · ASYNC_FAIL · DOWNLOAD_FAIL.

미검증 외부 사실: PixVerse 가격·모델명(V6/C1)·기능 등은 기획서 주장(unverified)이라 코드에 하드코딩하지 않고 환경설정(env)으로만 관리합니다.

알려진 부채 · 주의

  • 금전 정밀도: 와이어 금전값은 float(표시용 추정, FE z.number() 일치). DB 원장은 numeric/Decimal 정밀. 실 과금 API 도입 시 string decimal / minor-unit로 재검토 필요.
  • in-memory 스캐폴드: webhook 중복 방지·저장소가 단일 프로세스용 — 운영은 DB 영속 필요.
  • webhook 서명: 스캐폴드 제네릭 HMAC(ts+payload). 실 Provider 규격은 unverified이며, 이벤트 필드는 서명된 payload 본문에서 파생해야 함(로드맵).
  • Codex 외부검증: 3회 모두 미통과(캡 소진). 지적된 실버그는 수정·내부 재검증했으나, 수정본에 대한 Codex 재검증은 없음. “Codex 통과”가 아님.
